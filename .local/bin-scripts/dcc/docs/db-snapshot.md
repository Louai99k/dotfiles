# dcc db-snapshot

Snapshots a local PostgreSQL database into a new directory, using docker exec in data-management-db-1. Script: snapshot-database.sh. PostgreSQL tools run inside the container; no Python or host PostgreSQL installation is needed. Uses the explicit local Docker socket and local PostgreSQL Unix socket. Default PostgreSQL superuser: luay (override with --user ROLE).

Snapshot an application database into a new directory:

    dcc db-snapshot local_db ~/db-snapshots/before-wdcc
    dcc db-snapshot master_db ~/db-snapshots/master-before-changes

Options:

    --user ROLE  PostgreSQL role to connect as. Default: luay.
    -h, --help   Show this help. Nothing else runs, even with other options.

Runs pg_dump --format=custom --create, retaining object ownership, grants, triggers and policies. Also captures database owner/encoding/locale/tablespace, connection limit, grants, settings and comment in SQL sidecars. SHA-256 checksums cover the archive and metadata. Snapshot files are private and published only after successful dump. Avoid concurrent schema/database configuration changes while snapshotting. The default data-management container is PostgreSQL 16; scripts use its catalog layout.

The output directory must not already exist. Work happens in a temporary .dcc-snapshot.XXXXXXXX directory beside it, removed on failure. The final mv -T refuses to move that directory inside an output directory created concurrently. Metadata SQL uses one fixed placeholder, __DCC_RESTORE_DATABASE__, replaced only with the staging name generated by dcc db-restore.

Requires Bash, Docker and GNU coreutils. Restoring later also requires the existing local roles/tablespaces/extension packages. No cluster-wide roles, replication slots, server configuration or external tablespace files are backed up. Snapshot SQL is trusted executable PostgreSQL backup material; use your own snapshots.

No dumps, restores, tests or verification commands were executed while preparing this script.
